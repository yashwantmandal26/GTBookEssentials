# GTBOOK Essentials application audit

Reviewed 13 November 2026. Source version: 2.1.5, commit `bab186d5b3d46b02c2ce41946cfe6fdaf0e1f9ab`.

The review found **14 application issues: 2 high priority, 10 medium priority, and 2 low priority**, plus two separate workspace/development issues. These are supported by source traces or isolated reproductions. They do not imply that every possible defect has been discovered.

## Scope and validation

Reviewed the current `GTBookEssentials` application across its 41 C# files (including its test suite), hardware transports, firmware guards, performance/GPU/USB controls, power policies, lighting and animation, shortcuts, screenshots, persistence, desktop lifecycle, UI layout, updater, installation/uninstallation, launch scripts, build scripts, and CI. Also inspected the enclosing repository's release workflow and the app's validation documentation.

- Existing desktop regression suite: **109 passed, 0 failed** (`tests/run.ps1`).
- Release tooling: passed script parsing, atomic replacement, installer mutex and simulated device recovery checks (`tests/release-tools.ps1`).
- Fresh production compilation: passed; isolated output at `tests/out/audit/GTBook-audited.exe`.
- Additional isolated probes reproduced false Turbo fan feedback, inaccessible minimum-size controls, GPU error misrepresentation, and prerelease version collapse.
- Preview renders covered normal and compact layouts. The minimum-size failure is illustrated in `tests/out/audit-ui/Minimum-Lighting.png` and `Minimum-Settings.png`.
- No physical hardware settings, installed application, scheduled tasks, drivers, or release publications were changed. Application implementation files were not edited.

This was a source and software audit. Firmware behavior, actual GPU routing after reboot, shutdown USB charging, cold sign-in startup, fresh-Windows recovery, and extended hardware/resource testing remain unverified. Existing documentation also identifies these physical validation gaps. Graphify could not run because its runtime and Python are unavailable; review proceeded directly against source and executable software probes.

Priority: P1 = address before broad distribution; P2 = normal corrective work; P3 = lower-impact compatibility issue. Static findings describe reachable code behavior; hardware interference and security exploitation were not attempted.

## 1. [P1] Elevated updates execute from user-writable storage

**Location:** `app.manifest:4`, `src/Store.cs:9`, `src/AppUpdater.cs:304-311,337-362`.

The application requires administrator privileges. Its updater downloads to `%LOCALAPPDATA%\GTBookStable\updates`, checks a hash, closes the file, and launches that path with the elevated process's privileges. The ZIP path similarly executes an extracted installer script from user-writable storage. The local preferences directory was confirmed to grant the current user inherited FullControl.

**Trigger and impact:** another process running as the same user can replace the executable after verification but before launch, or tamper with extracted scripts. A checksum validates bytes at one point in time; it does not protect the subsequent execution path. This creates an elevation tampering opportunity.

**Solution:** stage executable content in an administrator-owned directory with a protected ACL; reject unexpected reparse points; verify the protected copy and preserve protection through execution. Apply the same policy to ZIP extraction and scripts. Use absolute paths for system executables. A longer-term improvement is an unprivileged UI/downloader with a narrowly scoped privileged hardware/install broker.

**Regression check:** run a medium-integrity fixture under the same account and verify it cannot alter staging files or directories between verification and execution. Test both EXE and ZIP paths. No exploit was run during this audit.

## 2. [P1] The performance monitor resumes device access while a conflict remains

**Location:** `src/PerformanceModes.cs:103-111`; related transaction sequence in `src/OemProtocol.cs:41-43`.

`ModeObserver.Watch` inspects conflicts every 40 loop iterations. Finding a conflict skips that one iteration and changes the interval to three seconds. The following iteration bypasses the conflict check, reads the device, and resets the interval to 60 ms, although the competing utility may still be running.

**Trigger and impact:** start a recognized competing controller while Essentials is watching mode changes. Both utilities can access the embedded controller. An OEM register read itself performs selector/command writes, so overlapping access can interleave protocol sequences and invalidate readings or actions. Physical interference was not exercised.

**Solution:** retain the blocked/conflict state until a fresh inspection confirms that the conflict has cleared. Check the gate immediately before an EC transaction; do not resume merely because a delay elapsed. Share one conflict policy across observers and command paths.

**Regression check:** inject a persistent conflict and assert zero provider calls for the entire blocked period; clear it and verify controlled recovery.

## 3. [P2] Turbo claims full fans when firmware does not confirm them

**Location:** `src/PerformanceModes.cs:18,29-36`, `src/Feedback.cs:40`, `src/MainWindow.cs:3641`.

The Turbo fan write suppresses exceptions. If fan read-back remains zero, `ApplyModeWithCooling` still returns `Ok=true` and `mode=Turbo`, alongside `cooling=Firmware auto`. Both feedback paths nevertheless announce **Full fans ON**.

**Reproduction:** the injected provider accepted the performance register but ignored the fan write. The safe harness returned:

```text
Ok=True; mode=Turbo; cooling=Firmware auto; fanWrites=1
Feedback=Turbo mode / Ultimate Performance · Full fans ON
CONFIRMED=True
```

Evidence: `tests/out/audit/TurboFanAudit.cs` and `turbo-fan-report.txt`. All provider operations were simulated.

**Solution:** represent partial application explicitly. Keep the confirmed Performance state or show a clear partial Turbo failure until full fans are verified. Generate feedback from actual cooling confirmation. Apply the same explicit error handling to failed automatic-cooling restoration on Turbo exit.

**Regression check:** cover ignored writes, thrown writes, delayed success, and permanently mismatched read-back. None may produce a confirmed full-fan message without confirmation.

## 4. [P2] Startup and ordinary mode changes overwrite the user's Windows power plan

**Location:** `src/EnergySaver.cs:211-221,294-306`, `src/MainWindow.cs:3670`.

Every Quiet/Balanced/Performance synchronization activates `ResolveNonTurboScheme`. Without a saved pre-Turbo plan, that resolver returns Windows Balanced. Initial mode observation invokes this synchronization, so opening Essentials can replace a user's custom or High Performance plan even if they never entered Turbo. A saved pre-Turbo plan can also override a different plan the user selected later.

Turbo ownership is not restored across an app restart: firmware raw mode 2 is rediscovered as Performance, the Windows Turbo plan can be restored away, and the full-fan override can remain. Inferring Turbo from raw mode 2 plus full fans alone would also be wrong because manual full fans are supported.

**Solution:** preserve the active base plan during ordinary mode synchronization. Restore a prior plan only when leaving an app-owned Turbo transition and the active plan is still the app-owned Turbo plan. Persist and reconcile ownership, then clear it after restoration. Preserve subsequent user changes.

**Regression check:** use an injectable power-plan backend. Verify first startup preserves a custom plan; entering/exiting Turbo restores it once; user changes win; restart during Turbo reconciles plan and fan ownership correctly. No power-plan APIs were called to reproduce this finding.

## 5. [P2] Running animations ignore some recognized conflicting controllers

**Location:** `src/ExtraEffects.cs:179-188`, `src/Core.cs:125`.

The animation monitor accepts only conflict messages containing case-sensitive fragments `ControlCenter`, `InfinixToolkit`, or `old Python toolkit`. The conflict detector also recognizes names such as `InfinixGTToolkit`, `Infinix Toolkit`, and differently cased process names. Those valid conflict messages can fail the monitor's filter.

**Trigger and impact:** start one of the omitted controllers after an Extra animation is running. The animation continues sending keyboard frames despite a recognized conflict.

**Solution:** treat every nonempty `Hardware.Conflict()` result as a conflict. Prefer structured conflict results over testing human-readable message text.

**Regression check:** enumerate every recognized controller name, including case variants, and verify the stream stops for each.

## 6. [P2] Rear “Turn off” is undone by restart or resume

**Location:** `src/MainWindow.cs:2298,636-639`; persistence gate at `3825-3829`.

The Turn off action sends `rear-off` with no save name and does not update the desired rear power preference. Initialization later reapplies the previously illuminated preset when its brightness is positive. Resume uses this initialization path as well.

**Trigger and impact:** apply an illuminated rear preset, turn it off, then restart the application or suspend/resume. The previously saved lighting can turn back on.

**Solution:** after acknowledged Off, persist a separate rear-enabled/resume flag and update the desired power state. Initialization must honor that state. Preserve the editable effect/colour preset so turning off does not erase the user's choices.

**Regression check:** Apply -> Off -> reload and Apply -> Off -> resume must remain off. A rejected Off command must not persist success.

## 7. [P2] Enabling “Keep keyboard awake” during an animation silently fails

**Location:** `src/MainWindow.cs:2932,3032`, `src/ExtraEffects.cs:196-198`.

Every live update forces `ArmKeyboardAwake=false`. The worker requires this flag to be true before sending the watchdog-disable command `0x19`, but the UI still marks the feature configured and saves the enabled preference.

**Trigger and impact:** start an Extra animation with Keep awake disabled, then enable it while the stream remains active. The preference says enabled without sending its required controller configuration.

**Solution:** send `ArmKeyboardAwake=request.KeepAwake` and let the worker's existing `!awake` guard deduplicate the write, or derive the flag from acknowledged worker state. Update the UI's configured state only after acknowledgement.

**Regression check:** a false-to-true live change sends exactly one `0x19`; repeated enabled updates send none; failures do not mark configuration successful.

## 8. [P2] Supported small windows hide actions without allowing scrolling

**Location:** `src/MainWindow.cs:309-320,437,699-794,1024`.

The window allows small sizes while its main page has `AutoScroll=false`. Width reflow does not guarantee that the resulting content fits vertically. The existing layout test explicitly omits vertical overflow checks below width 860.

**Reproduction:** an isolated preview at the production-equivalent minimum size of 950x700 on this desktop's 125% scale produced a 932x653 client area. Lighting extended 138 px below its page viewport; Settings extended 216 px; Overview extended 107 px. Lower controls, including lighting actions, are inaccessible. Preview and production minimum sizing were accounted for separately.

Evidence: `tests/out/audit-ui/ui-audit-report.txt`, `UiHarness.cs`, and the `Minimum-*.png` renders.

**Solution:** allow vertical scrolling when the page's content exceeds its viewport, or use responsive sections/paging that keep every action reachable. Keep a realistic minimum size compatible with the available work area.

**Regression check:** measure complete reachable content at the actual minimum outer window size, short work areas and multiple DPI scales. Remove the small-width test exemption and revise the assertion that scrolling must always be disabled.

## 9. [P2] GPU read errors and pending requests are presented as active hardware state

**Location:** `src/Core.cs:255-262`, `src/MainWindow.cs:3521-3535`, `src/GpuModes.cs:34`.

Arbitrary GPU read failures are emitted as `Unavailable: ...`. The UI treats all unavailable readings as evidence of a sleeping/inactive GPU. Also, applying a GPU request updates `gpu-mode` immediately, before reboot; that requested value influences the claim that the dGPU is off.

**Reproduction:** a preview fed `Unavailable: Device busy; reading deferred.` displayed **Idle / iGPU only · dGPU off**. This was a simulated sensor error, not proof of inactive hardware.

**Solution:** return typed sensor statuses: successful value, known sleep condition, unknown, and error. Display Unavailable/Could not read sensor for errors. Keep requested firmware mode separate from observed active routing, and avoid active-power claims without evidence.

**Regression check:** busy, access-denied, transport failure, verified sleep and pending GPU requests must produce distinct truthful states.

## 10. [P2] A Start-menu launch can silently leave the application hidden

**Location:** `release/Start.ps1:6`, `src/Program.cs:234-235`, `src/AppSignals.cs:13-17`.

The launcher starts the scheduled task with `--startup`, waits exactly 400 ms, attempts the Show event once, and exits successfully even if the event does not exist. The application creates its signals only after constructing MainWindow.

**Trigger and impact:** on a cold or loaded system taking more than 400 ms to reach IPC readiness, explicitly opening the app starts it in the tray but does not show its window.

**Solution:** retry the foreground/show handshake until readiness or a bounded timeout. Confirm delivery, provide a useful fallback on failure, and distinguish explicit foreground launch intent from automatic sign-in startup.

**Regression check:** simulate signal readiness after 400 ms and after several seconds; the explicit open action must show the window once and not create duplicate processes.

## 11. [P2] Installer rollback omits metadata and shortcuts

**Location:** `release/Install.ps1:87-104`.

The installer writes `install-state.json`, common Start-menu shortcuts, and HKLM uninstall metadata before starting the task. Its catch restores payload files and scheduled-task settings, but not those other artifacts.

**Trigger and impact:** failure during shortcut creation, registry writes, or final task launch can leave dead shortcuts/uninstall entries after a fresh installation, or metadata claiming a new version while an upgrade restored the old executable.

**Solution:** include the state file, shortcut files and uninstall key in the transaction snapshot and rollback. Remove newly created artifacts on fresh-install failure, restore previous metadata during upgrade failure, and preserve OEM startup restoration data. Make rollback resilient enough that one restoration failure does not skip the remaining restorations.

**Regression check:** inject failures after every commit step in a simulated installer environment and verify all prior files, tasks, metadata and shortcuts are restored. Actual installation/uninstallation was not run.

## 12. [P2] RC tags can enter the stable channel and collapse to the final version

**Location:** `.github/workflows/build.yml:23-38,73-91`, `src/AppUpdater.cs:60-82,132-138`.

The workflow accepts `v*` tags, strips prerelease suffixes from package/application versions, and creates new GitHub releases without `--prerelease`. The updater excludes releases based on the API flag, but strips suffixes itself when comparing versions.

**Reproduction:** parsing a mocked `v2.2.0-rc.1` release with `prerelease=false` against installed 2.1.5 yields an available update displayed as `v2.2`. `rc.1`, `rc.2` and final `v2.2.0` all parse to `2.2.0.0`; the final release is consequently not newer than the corresponding installed RC.

**Solution:** explicitly mark suffix-bearing releases as prereleases in CI, preserve the full informational version, and use SemVer ordering with a deliberate stable/preview channel policy. Handle existing release metadata as well as newly created releases.

**Regression check:** stable users never receive an RC; preview users can advance RC1 -> RC2 -> final; final is newer than every RC for that version.

## 13. [P3] External keyboards lose their normal Insert key behavior

**Location:** `src/Screenshots.cs:15-19`, `src/LaptopShortcuts.cs:93-95`.

The laptop's shared Insert/PrtScn workaround consumes every extended Insert event globally. Standard Insert keys on external keyboards use this event too. Disabling the F1/F2/F3 preference does not disable screenshot interception.

**Trigger and impact:** press ordinary Insert on an external keyboard while Essentials is running. It can capture a screenshot instead of allowing the focused application's Insert behavior.

**Solution:** provide independent screenshot interception and OEM Insert-remap preferences. Keep ordinary Insert available unless the remap is enabled; consider device-specific handling if reliable device identification is implemented.

**Regression check:** OEM remap, external Insert, numpad Insert, modifiers and disabled interception must be tested independently.

## 14. [P3] A completely full disk is reported as unavailable free space

**Location:** `src/DeviceInformation.cs:30,57`, `src/DeviceSpecView.cs:248`.

The shared byte formatter returns Unavailable for every value less than or equal to zero. Storage reporting uses it for free space too, where zero is a valid and important value. A full disk is therefore reported as `Unavailable free of ...`; the device view cannot parse the expected capacity pair and omits the usage bar.

**Solution:** distinguish missing/invalid capacity from a valid zero. Allow zero for free-space formatting, or introduce a dedicated formatter. A valid full disk should display zero free and a 100%-used bar.

**Regression check:** cover zero free bytes, positive free bytes, and missing capacity independently. This is a source-confirmed formatting edge case; no disk was filled during review.

## Separate repository and development issues

These do not describe the shipped nested application's normal runtime.

1. **Stale parent release workflow:** the enclosing repository's `.github/workflows/release.yml:18` uses `Infinix_Toolkit` as its working directory, but that directory is absent from the current reorganized working tree. The parent remote is `Infinix-GT-Book-Custom-Control-Center`; `GTBookEssentials` is a separate nested repository with its own workflow. If the current parent reorganization is committed/pushed, its old release workflow will fail. Update/remove that workflow according to which repository is intended to build the app. Preserve the two repositories' histories deliberately.
2. **Local “latest startup” recovery can select an older build:** `Launch-Latest.ps1:13-24`, `Fix-Latest-Startup.ps1:19-30`, and `release/Launcher.cs:21-60` can route startup back through a launcher that reruns the same task and ultimately falls back to the adjacent older executable. These recovery files are ignored/excluded from release inputs. Resolve and verify the intended latest executable first, gracefully exit a different running build, then launch the resolved executable directly.

## Recommended repair order and broader improvements

1. Protect elevated update staging and fix both conflict-monitor paths.
2. Correct Turbo confirmation and power-plan ownership; make partial hardware outcomes explicit.
3. Repair persistent Off/Keep-awake behavior and small-window reachability.
4. Separate GPU requests, sensor errors and observed state.
5. Add startup handshake, transactional installer rollback and proper release channel/version tests.
6. Add the external-keyboard preference and align the README/version/validation evidence with the actual release.

The existing suite gives useful coverage of packet composition, read-back success paths, animation continuity, UI components and atomic file writes. The missed cases are mostly cross-feature transitions and failure paths. Add targeted regression checks for the findings above instead of relying only on more success-path examples.

For maintainability, split the 3,892-line MainWindow into page/view components, command orchestration, and explicit state models. Inject hardware, power-policy, startup and update-staging interfaces so failures and delayed completions can be tested without physical writes. Replace string parsing of statuses/conflict messages with typed results. Consider an opt-out for automatic update checks to make the app's offline behavior clear. Measure tray-idle CPU, wakeups, memory and battery use before choosing a different mode-observer polling rate.

Completion criteria should include physical validation of the documented hardware gaps on the supported GL613/BIOS 1.00 profile, plus fresh-install, upgrade, rollback, uninstall, reboot/sign-in and suspend/resume checks. Passing the current software suite alone is insufficient evidence for those outcomes.
